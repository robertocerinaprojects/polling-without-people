# Repository conventions

These conventions apply to `01_frame`, `02_personae` and `03_mrp`.

## Shared component layout

| Path within a component | Purpose |
|---|---|
| `README.md` | Authoritative execution-order and implementation-status index |
| `scripts/` | Numbered analysis scripts |
| `docs/` | Companion documents, decision notes and versioned source manifests |
| `data/input/` | Unmodified external source snapshots |
| `data/intermediate/` | Generated working datasets consumed by later processing |
| `data/output/` | Audit tables, exports and eventual component deliverables |

The shared R environment and Codespaces configuration stay at repository root.
Empty required directories use `.gitkeep` placeholders.

Component prefixes establish the overall order: `01_frame`, `02_personae`, then `03_mrp`.
Script numbering remains local to each component.

Each component has one README at its root. Individual script
explanations belong in `docs/`; there is no additional README inside `scripts/`.

## Naming and execution

- Use lowercase, descriptive names with underscores for project-authored files.
- Shared implementation for a numbered step belongs in `scripts/helpers/`.
  The parent script and its companion guide identify its helpers and inputs.
  Drawing code and the corresponding publication figure can live together in
  `docs/figures/`.
- Scripts use two-digit prefixes: `NN_verb_object.R` or `NN_verb_object.py`.
- Numbering is local to each component and follows the intended execution order.
- The main companion document has the same basename: `NN_verb_object.md`.
- Supporting notes and manifests use the related step prefix, such as
  `02_cvap_allocation_decisions.md` or `02_pl_2020_sources.csv`.
- Figures supporting documentation belong in `docs/figures/`, when needed.
- Keep standard names such as `README.md`, `LICENSE` and the `.R` extension.
- Preserve official input filenames and established validated data paths.
- Audit/export filenames should identify their producing step.
  Reusable intermediate datasets may use stable descriptive names.
- Run scripts from the repository root. Document prerequisites explicitly.
- Any future runner must list intended scripts explicitly; it must not
  recursively execute every script it finds.

## Implementation status

| Status | Meaning |
|---|---|
| `planned` | Work is identified but no implementation is available |
| `draft` | Implementation is incomplete or its execution has not been reviewed |
| `validated` | The documented checks passed for the recorded inputs |

Validation evidence belongs in the script's companion document: inputs,
checks, results, limitations, and the tested date or commit where known.
A component containing validated steps is not necessarily complete.

Keep the current status table in the component README. Other overview pages
link to it rather than maintaining duplicate execution lists.

## Input and output documentation

Each component will maintain `docs/data_catalogue.md`. This is the
authoritative inventory of its data files, including generated intermediates,
audit outputs and script-generated documentation.

For each external input, record:

- Repository-relative path, source organisation and exact source URL.
- Release/version, file fingerprint and acquisition instructions.
- Whether acquisition is currently manual or implemented by a script.
- Format, relevant columns and keys, population universe, units and geography.
- Scripts and sections that read it, and the products it contributes to.

For each generated artifact, record:

- Repository-relative path and producing script/section.
- Exact upstream inputs, including generated inputs from earlier steps.
- Downstream consumers, including consumers in another component.
- Relevant schema/keys, meaning, validation evidence and implementation status.
- Whether the artifact is the authoritative dataset or an export of another file.

The catalogue must support tracing both input -> script -> output and
output -> producing script -> inputs. Distinguish direct dependencies from
products reached through later steps.

Script documents list their exact inputs and outputs and link to the catalogue.
Existing source manifests can hold detailed checksums; the catalogue should
link to them rather than maintain conflicting copies.

Downloaded inputs, working datasets and model fits stay local. Git records the
source manifests, checksums, instructions and methodological decisions. For the
House validation, it also records the published figure and four CSVs (district
split, sampler diagnostics, district predictions and scores). Find their run
directory under `01_frame/data/output/09_beta_holdout/` using
`latest_complete.txt` in that folder.
Reference another component's authoritative dataset by its documented path;
record any intentional copying or transformation.

## Generated documentation

Some documents are generated by scripts. Record their writer in the catalogue
and change their generating code when changing the generated explanation.

Current examples are `01_frame/docs/02_cvap_suppression_audit.md` and
`01_frame/docs/02_ct_cvap_identifier_audit.md`, written by Script 02.
Any relocation must update the writer and its links together.

## Script documentation

As we review each numbered script in `01_frame`, `02_personae` and `03_mrp`, we
maintain a companion document in that component's `docs` folder, using
the same numbered basename. The script header links to its document.

Each companion document begins with a **Plain-language summary** written
in short, conversational paragraphs. It explains what data we start
with, what we are trying to achieve, how the main steps work, which
assumptions we make, and what the resulting output will be used for.
It distinguishes supplied data from quantities we estimate.

Technical details, source references, commands and validation results
follow the summary. Intended behavior is clearly distinguished from
implemented and validated behavior.

Supporting decision or audit documents should also briefly explain
their purpose in plain language and link to the main script document.
When a document is generated by a script, its explanation must be
maintained in the code that generates it.

We update these explanations as each script is reviewed and refined.
